# Test Scenario Catalogue

This is the single source of truth for what gets tested. Every automated test title MUST start with the scenario ID it
implements (for example `it('TS-QA-08 confirm matrix: statusBar × firstTime × acknowledged', …)`), so the traceability
check ([TS-QA-50](#ts-qa)) can prove that every non-manual scenario is automated.

- Strategy, tooling and exit criteria: [TEST-STRATEGY.md](TEST-STRATEGY.md)
- Live user testing checklist: [UAT.md](UAT.md)
- Design under test: [ARCHITECTURE.md](ARCHITECTURE.md)
- Behaviour source: engineering spec v2 (§ numbers below refer to it).

## Conventions

| Item          | Meaning                                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Priority      | **P0** safety/data-integrity, release-blocking. **P1** core behaviour, release-blocking. **P2** quality/polish, fix or waive.        |
| `unit`        | Vitest, pure code with fakes (`test/unit/**`). Adapter/extension units use a `vscode` module mock (see [Notes](#notes-for-test-eng)) |
| `property`    | Vitest + fast-check, seeded, generative or model-based (`*.property.test.ts`).                                                       |
| `static`      | Vitest tests that inspect files, the manifest, the bundle or the VSIX (`test/unit/static/**`), plus CI grep steps.                   |
| `integration` | `@vscode/test-cli` label `integration`, real VS Code extension host, isolated profile (`test/integration/**`).                       |
| `policy-CI`   | `@vscode/test-cli` label `policy`, Linux CI only, `/etc/vscode/policy.json` (`test/policy/**`).                                      |
| `e2e`         | Playwright `_electron` driving real VS Code UI (`test/e2e/**`).                                                                      |
| `mutation`    | Stryker on `src/core/**` + `src/ui/presentation.ts`.                                                                                 |
| `manual-UAT`  | Human tester in the `npm run uat` sandbox, recorded in [UAT.md](UAT.md).                                                             |

### Fixtures used in steps

- `S(eff, def, glob)` = `AutoApproveSnapshot { effective, defaultValue, globalValue }`. `def` defaults to `false`.
- **FakeSettings** — in-memory user value; `targetId` (default `'local'`); optional `policy` value (effective = policy,
  every write throws `Unable to write to User Settings because chat.tools.global.autoApprove is configured in system
policy.`); optional `override` (another layer wins, writes succeed but effective does not follow); `failNextWrite(msg)`;
  records every `writes[]`; fires `onDidChange` **synchronously inside** `writeUserValue` when the stored value changes
  (models §2: this window's event fires before the `await` resumes). Identity writes fire nothing.
- **FakeStorage** (Map; `failNextUpdate(msg)`), **FakeConfirm** (scripted or deferred answers; records `calls`),
  **FakePrefs** (`confirmBeforeEnabling`), **SpyLogger** (captures lines by level).
- "Stash for T" = `{ v: 1, target: T, value?: … }` under `copilotAutoApproveToggle.stash.v1/<T>` (one key per target;
  `T` is `'local'` or `remote:<remoteName>:<authority>`, recomputed on every access). "Ack" =
  `copilotAutoApproveToggle.riskAcknowledged.v1`.
- "Nothing written" = `FakeSettings.writes` is empty, or contains only identity writes when the scenario says so.

## Notes for test-eng

- **Title prefix**: every automated test title begins with its scenario ID; TS-QA-50 enforces it.
- **Forbidden key**: do not put the forbidden context-key string anywhere under `test/` — not even in a test that checks
  for its absence. The check lives in the CI workflow grep (TS-QA-48 a).
- **`vscode` mock for adapter units**: add a Vitest alias `vscode → test/unit/__mocks__/vscode.ts` (minimal fakes for
  `window`, `workspace`, `commands`, `env`, `MarkdownString`, `StatusBarAlignment`, `ConfigurationTarget`, `ThemeColor`).
  Coverage thresholds apply only to the pure modules; adapter units still run in the same Vitest job.
- **Status-bar origin in integration**: integration tests cannot click the status bar or answer modal dialogs (VS Code
  refuses dialogs under `--extensionTestsPath`). In `ExtensionMode.Test` only, `activate()` exports
  `testing.statusBarNonce`; integration tests pass it to `copilotAutoApproveToggle.toggle` with
  `confirmBeforeEnabling = never` so no dialog is needed. Accept/decline dialog paths are covered by unit tests (fake
  `ConfirmPort`, captured `item.command.arguments[0]`) and E2E (real click, real modal).
- **Dialogs in integration**: no real modal is ever shown or answered in integration. Tests either avoid the dialog
  (nonce + `never`, or ack in `firstTime`) or replace `vscode.window.showWarningMessage` with a stub (the test bundle
  shares the extension's `vscode` API object) that records the request and returns a scripted answer. Answering the
  real dialog (accept / Cancel / Esc) is covered only by unit tests and E2E (USR-02/03/05/10).
- **Never automate VS Code's own "Enable global auto approve?" dialog** and never trigger agent tool calls in automated
  tests; that prompt is covered only by manual UAT.
- **Policy**: TS-ADM-01/04 run in the canary phase, TS-ADM-02/03 in the locked phase (`POLICY_PHASE`).
- **Missing scripts/deps** (request via lead): `test:e2e` (Playwright), `test:mutation` (Stryker), `@playwright/test`
  or `playwright-core`, `@stryker-mutator/core`, `@stryker-mutator/vitest-runner`.
